# Стендова перевірка 4.0

Перевірка розпочата: ESP32-C3 Super Mini підключено через USB.
Esptool підтвердив ESP32-C3 QFN32 rev 0.4, flash XMC 4 МБ, USB Serial/JTAG.
Не прирівнюйте успішну компіляцію чи браузерні fixtures до роботи на залізі.

## Перед прошивкою

- Встановити точну модель ESP32, flash, pinout і підключення USB.
- Для ESP32-C3 Super Mini — USB CDC увімкнено; GPIO20 залишається для LED.
- Перевірити 0x62, основну I2C 8/9 та OLED software I2C 3/4.
- Перевірити резистори KY-016, спільний катод, напругу ADC TEMT6000.
- Вибрати Minimal SPIFFS із двома OTA-розділами. Перший flash через USB.

## Автономна робота

1. Старт у темряві/при світлі: LED не блимає денною яскравістю до вимірювання;
   OLED спочатку показує доступ, далі вимірювання. Записати час першого виміру.
2. Від’єднати SCD40: веб показує null, OLED помилку, LED згасає;
   повернути сенсор — автоматичне відновлення. Повторити кілька разів.
3. Перевірити normal і eco: відповідно ~5/~30 с; eco не перезапускається кожні 15 с.
4. Перевірити кольори й відсутність тремтіння біля меж. На нічній яскравості
   порівняти синій/фіолетовий/помаранчевий. Нуль LED має справді його вимикати.
5. Провести двоточкове калібрування світла; занести середні/шум/мінімум/максимум.
6. Провести optical test зі сталим зовнішнім світлом. За впливу індикації на ADC
   додати непрозору перегородку; це неможливо виправити універсальною константою.
7. Закриття/відкриття світла, короткі спалахи, нейтральний діапазон, нічне гасіння.
8. Перевірити жест у світлі; у темряві та під час optical test він не має діяти.
9. Перевірити всі OLED-сторінки, п’ятизначне CO₂, зміщення та пробудження.

## Веб і мережа

1. Новий пристрій: WPA setup AP → login з OLED → збереження Wi-Fi → домашній IP.
2. Неправильний пароль і відсутня мережа: через 60 с доступний setup AP;
   ADC/SCD40/OLED продовжують працювати. Зміна Wi-Fi через USB без кнопок.
3. Вимкнений Wi-Fi: recovery AP першу хвилину; після відключення телефона
   радіо вимикається. Новий запуск/USB access знову дає доступ.
4. Дві вкладки: зберегти зміни в першій, спробувати зберегти стару другу — 409.
5. Перевірити відхилення неправильного пароля, POST без request header,
   завеликого JSON, некоректних калібрувань; паролі відсутні в backup/settings.
6. Preview яскравості не змінює збережені налаштування; за 10 с завершується.
7. HomeKit: сполучення, числові покази, LED switch, fault при від’єднанні сенсора,
   повторне сполучення після скидання. Зафіксувати версії iOS і HomePod/Apple TV.
8. MQTT із Mosquitto/HA: discovery, відсутність дублювання сутностей, offline
   при втраті сенсора/живлення, перепідключення після рестарту брокера.

## Дані, калібрування й OTA

1. Записати добу: правильні min/max/trend, прогалини при відсутності сенсора,
   CSV та часові мітки після NTP. Підсумок ночі рахує тільки спостережуваний час.
2. Архів: форматування → увімкнення → запис за 15 хв → вимкнення живлення →
   відновлення останніх 24 год після NTP. Зупинка живлення під час знімка
   не повинна знищити обидві копії. Дані старші доби не показуються як поточні.
3. Провітрювання: ручний старт/стоп, автоматичне завершення після 60 с нижче
   цілі; втрата сенсора скидає підтвердження, не оголошує успіх.
4. Self-test: результат із сенсора, I2C/UI не зависають на 10 секунд.
   FRC — тільки з відомим еталоном, за процедурою виробника.
5. Offset: порівняти з еталонним термометром після теплової стабілізації корпусу.
   ASC обрати відповідно до реального провітрювання; довільне калібрування не робити.
6. OTA правильного application image → 60 с health check → нова версія.
   Пошкоджений/інший чип/інший проєкт/порожній upload відхиляються.
7. OTA тестової версії, яка не проходить health check, → відкат до попередньої
   після 180 с або невдалого boot. Переконатися, що налаштування зберігаються.
8. 24–48 год роботи з відкритою панеллю, HomeKit та MQTT: записати minimum heap,
   reset reason, число I2C errors і відновлень. Перевірити, що ріст журналів обмежений.

Корпус: SCD40 біля отвору для обміну повітрям, відокремлений від нагріву ESP32,
регулятора й дисплея. Перевірити живлення під піковим навантаженням датчика/Wi-Fi.
Без схеми й вимірювань неможливо підтвердити електричну та теплову оптимальність.

## Watchdog на слабкому Wi-Fi: діагностика 4.1.1

Після тесту у спальні реальний API 4.1.0 повернув reset_reason=6
(ESP_RST_TASK_WDT), RSSI=-71 dBm, TX=13 dBm. У журналі поточного запуску:
AP на 59-й секунді, домашній Wi-Fi на 199-й. USB у цей момент відсутній.
Це підтверджує watchdog-перезапуск, але не його точний стек.

Виявлений дефект: NetworkClient::write має 10 спроб select по 1 с;
повільний TCP-клієнт може перевищити наш 10-секундний task watchdog.
4.1.1 обмежує HTTP response write до 2.5 с загалом / 500 мс без прогресу
через неблокувальний send, закриває недописаний запит. Історія має точний
Content-Length замість chunked footer, який обходив перевизначений write.
Watchdog не вимикається. HomeKit та вхідний HTTP parser — окремі шляхи,
які це виправлення не оголошує перевіреними чи повністю неблокувальними.

`python3 tests/network_write.py`: PASS; фактичний клас із скетчу перевірено
на локальних socketpair зі звичайним, зупиненим та повільним читачем,
включно з відновленням наступного запиту.
Діагностика `previous_network_stage`: 0 поза відміченими операціями,
1 HomeKit, 2 HTTP, 3 MQTT, 4 archive, 5 setup; RTC зберігає останній
маркер при програмному перезапуску. При повному знятті живлення RTC
не є надійним сховищем. `http_aborted_responses` — лічильник обірваних відповідей.

Фінальна компіляція 4.1.1: PASS, встановлений Arduino-ESP32 3.3.11,
flash 1779275 / 1966080 (90%), RAM 80144 / 327680 (24%).
На момент завершення збірки USB відсутній і HTTP не відповідає;
4.1.1 ще не записана, усунення обривів у спальні не підтверджено.
